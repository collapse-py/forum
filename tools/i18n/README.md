# 批次翻譯工具（tools/i18n）

`../..//README.md` 的「批次翻譯的作法」一節描述的流程。代理模型只負責中間那一段
（讀 TSV、寫 TSV）；切工作單與合併成 TS 都是這裡的腳本做，因此翻譯品質的驗證
不依賴代理模型自報。

全部從 `frontend/` 目錄執行（它們讀寫 `src/i18n/` 相關路徑）。

## 用法

```bash
# 1. 切工作單：把 messages.ts 抽成 key<TAB>原文，切成每份約 96 行
node ../../tools/i18n/make-worklist.mjs <輸出目錄> <語言> [份數，預設 4]

# 2. 交給代理模型，每個任務一份：讀 <語言>-N.tsv，寫 <語言>-N.out.tsv

# 3. 合併：鍵集 / 佔位符 / 未翻譯殘留都過關才會寫出 TS 檔
node ../../tools/i18n/merge-translations.mjs <輸出目錄> <語言> <匯出名稱> <檔名>
#    沒收齊會輸出 <語言>-todo.tsv，遞迴回第 1 或第 2 步

# 附帶：把 todo 再切小
node ../../tools/i18n/split-todo.mjs <輸出目錄> <語言> [份數]

# 任何時候都可以驗證全部目錄
node ../../tools/i18n/verify-catalogs.mjs
```

## 這幾個腳本為什麼長這樣

- **`make-worklist.mjs` 排除 11 個必須原樣保留的鍵。** 它們是拉丁字母的排版裝飾
  與產品名（`NEW POST`、`Admin Console`、`ID`…），翻譯會破壞視覺設計，而且它們本來
  就不需要翻 —— 少一類失敗原因。
- **`merge-translations.mjs` 以「鍵」為準，完全不在意分段。** 分段只是代理模型的
  輸入單位，對輸出格式沒有影響，所以「2 段改 4 段」與「某段重跑」都不需要考慮
  其他段。它同時是品質關卡，四種失敗的處理見 README 的表格。
- **佔位符不修復只報錯。** `{id}` 被寫成 `#id` 時，猜「大概是這個意思」而自動補
  上去，會讓一條翻錯的譯文看起來通過驗證 —— 那比直接失敗更糟。
- **`verify-catalogs.mjs` 的 Han 檢查排除中文與日文。** 日文介面裡出現漢字是正常
  的，用它判斷「未翻譯」只會產生噪音。
- **`verify-catalogs.mjs` 另外擋 `U+FFFD`。** 那是解碼失敗的替代符號，不是任何一種
  語言的字：它代表某個字元在編碼往返中被換掉且原始位元組已丟失，因此不能靠重譯
  修好。鍵集、佔位符、順序在這種情況下全部正常 —— 實測抓到過兩處 `th` 的損毀，
  都是因為「整句還看得出大致意思」而被當成可接受的翻譯擱置了。
