# 已知問題

誠實記錄現況，避免下次 deploy 時踩到。每條都標出**它的取捨是刻意的還是真的缺口** ——
兩者的處理方式完全不同：刻意的取捨要寫進文件，缺口要排進待辦。

## A. 測試缺口

**`httpapi` 約 14,500 行，仍有約 13% 沒有測試覆蓋。** 合併兩個 Go 模組的整體覆蓋率約
**87.7%**（2026-10-21 實測；CI 地板 75.0，逐套件各 ≥ 75.0%）。已覆蓋的是 CSRF、限流、CSP、殼檔同步、
貼文／留言編輯的授權與驗證邊界、圖片的所有權與刪除、收藏、RSS 與軟刪除的還原；
**其餘 handler 邏輯仍未涵蓋**。

剩下的缺口集中在三處，都不是「數量」問題而是「需要真的 MySQL／真的連線」：

1. `httpapi` 的 Elasticsearch 分支（索引重建、對帳）—— 沒有 ES 時只測得到降級路徑
2. `httpapi` 的背景工作（重建索引、定時對帳）—— 靠 tick 觸發，測試裡不會真的等
3. `forum/purge` 的清理排程與 `forum/audit` 的稽核清理在**真實 MySQL** 之外的行為 ——
   sqlmock 只能斷言 SQL 的形狀，「DELETE 之後 SELECT 看不到」這種問題只有真實 MySQL 答得出來
   （CI 的 `migrations` job 有真實 MySQL，但本機的 `go test ./...` 不會）

**`forum/data` 的遷移測試與 `forum/httpapi` 的子樹刪除測試需要真實 MySQL**，本機執行時會全部跳過（未設
`FORUM_TEST_MYSQL_DSN`）。CI 的 `migrations` job 會跑它們 —— 但那也意味著
**本機的 `go test ./...` 不會驗證 schema 遷移與留言子樹刪除的 SQL**。

## B. 架構取捨（刻意）

### 監控統計只活在一個行程裡

請求總量、依路由統計、延遲直方圖與每 IP 統計都是記憶體內的累計，**重啟歸零**。

分鐘桶會寫進 `forum_request_metrics`（已結束的分鐘、每分鐘只寫一次、用累加語意支援多
執行個體），因此時間軸在重啟後不會變空白，但「上個行程一共服務了多少請求」這種問題
答不出來。要長期資料得看存取日誌。

**多執行個體時監控頁只顯示打到這個行程的流量** —— 限流器的 hits map 本來就是行程內的，
請求統計沿用同一個範圍；資料庫的分鐘彙總會把各個個體加總，但即時統計不會。

### 每 IP 統計刻意不落盤

落盤會讓「某個位址在什麼時候打了本站」變成一份**永久的訪客紀錄**，而這一頁只需要
「現在正在怎樣」。重啟後歸零是這個取捨的代價。

若部署上真的需要長期的來源統計，那應該是**存取日誌**的工作（那裡本來就有 IP），而不是
從監控頁擴張出去。

### 來源位址的清單上限 200 個，會被驅逐

位址是攻擊者可控的維度（可偽造 `X-Forwarded-For`），因此 map 一定要有上限。驅逐掉的那
個位址，其計數會**整筆消失**（沒有併進任何彙總槽 —— IP 在這個頁面上是可操作的，彙總槽
裡的假位址無法操作也沒有意義）；`stats.clientsDropped` 是唯一的線索，介面會把它顯示出來。

### 被強制殺掉的行程仍會遺失當前分鐘的監控資料

`SIGKILL`、容器被硬殺、或排空超過 `SHUTDOWN_TIMEOUT_SECONDS` 之後被部署端殺掉。

優雅停止會在關機流程中寫出最後一次分鐘彙總（與背景工作收尾併行），因此「正常重啟」不再
有這個缺口；剩下的只有非正常結束。那與「監控本來就是取樣」相符，但確實是一個已知的資料
缺口。

### 延遲分位數是分桶上界

P95 只會落在 1/2/5/10/25/50/100/250/500ms 或 1/2/5/10s 上。介面上照實標示，但拿它跟
精確的 APM 數字比較會失望。

精確分位數要保存每次請求的耗時，記憶體會隨流量線性成長。

### 稽核紀錄的 INSERT 與操作共用交易

因此**稽核表故障會讓後台寫入全部失敗**（磁碟滿是最常見的原因）。這是刻意的取捨：寧可
「停權按了沒反應」，也不要「停權成功了但沒人知道是誰停的」。唯讀頁面不受影響。

### 稽核紀錄保存的是截斷後的文字

每個值 200 bytes。要還原完整內容得回 `forum_posts` / `forum_post_comments`，而那兩張表
的內容本身已經被覆寫了 —— **稽核紀錄不能回答「被改掉的那段原文是什麼」**，只能回答
「原本的前 200 bytes 是什麼」。

### 稽核紀錄沒有防止同一管理員互相掩蓋的機制

要查到「誰動的」需要該管理員的**存取日誌與稽核紀錄一起看**；而 access log 沒有輪替
設定，會無限期增長。

### 強制登出的稽核紀錄可能在動作之後才寫

稽核在 MySQL、動作在 Redis，兩者不在同一個交易裡。稽核寫入失敗時**操作已經生效**，介面
會明確說明這一點。

它看起來像矛盾，但那正是「寧可少一筆紀錄，也不要一筆不實的紀錄」這個取捨的樣子。

### Session 不記錄 IP 與 User-Agent

因此**無法從後台看出「這支 session 是從哪裡來的」**。這是「token 即憑證」設計的已知
限制（token 不輪替、不綁 IP/UA，遭竊的 cookie 在過期前可完整重用），而不是這個功能漏了。

刻意不補：為了診斷而擴大憑證的儲存面不值得；而且補上這兩項也不會讓 token 竊取本身消失。

### Session 列表的建立時間只對新建立的 session 有意義

`created_at` 是這個功能之後才寫進 hash 的，既有 session 顯示「未知」且**永遠不會補上**
（建立時間已經過去了，補寫不可能，猜一個值只會產生比「不知道」更糟的資料）。

### Session 掃描有 20000 個 key 的上限

達到時清單不完整（介面會標示）。在同時登入人數遠低於這個數字的站上不會發生；一旦發生
（例如爬蟲大量登入），**強制登出會回 409 而不是靜默宣稱成功**。

### IP 封鎖在 Redis 故障時失效（fail open）

擋掉所有人會把一次 Redis 抖動變成「整站不能發文」，那比封鎖失效嚴重得多（Redis 掛掉時
本站的登入本來就已經受影響）。

代價：攻擊者只要製造 Redis 壓力，就能暫時解除對自己的封鎖。**監控頁的 Redis 探測是這個
狀態唯一的提示。**

### IP 封鎖在超過 365 天時被就地收斂

不會回錯。介面上寫出了上限，但匯出的稽核紀錄只會記到**收斂後**的到期時間。

### IP 封鎖的「原因」不存進 Redis

只存在稽核紀錄裡。因此**從 Redis 直接查（redis-cli）會看不到原因**，而那些紀錄在稽核
保留期（90 天）到期後就消失了。

### 內容趨勢的每日份量以主機本地時區切分

站台在 UTC、管理員在 UTC+8 時「今天」會看起來少一截。這是 `created_at` 寫入
`time.Now()`（而非資料庫的 `NOW()`）的必然結果，介面上已寫出這一句，但它仍是需要管理員
自己記住的背景知識。

### 內容趨勢的「熱門標籤」不受時間視窗限制

而「熱門文章」與「活躍作者」受限制。這個不一致是刻意的（標籤是身分分類、其餘是事件），
但讀排行榜時若不注意到就會拿三份**不同範圍**的資料互相比較。

### `/admin/stats` 的日別序列最多落後十分鐘

日別新增量讀 `forum_daily_stats`（見 [`DATABASE.md`](DATABASE.md)），由背景排程每 10 分鐘
重算最近三天；剛發生的事件因此最多晚 10 分鐘才出現在趨勢圖上。啟動時
`BackfillDailyStats` 會先補上缺漏的日期，所以重啟不會留下空白。

熱門文章與活躍作者仍是即時查詢，掃描量被 90 天視窗限制住，而不是被預先彙總。

### 這次改動之前留下的孤兒檔無法清除

貼文附圖與頭像現在都能換、能移除，舊檔在**不再被任何貼文或頭像引用**時會被一併刪除
（見 [`API.md`](API.md#貼文附圖與頭像的替換)）。但「這張圖是誰上傳的」是從 `forum_media`
的紀錄回答的，而那是這次改動才開始寫入的表 —— 在它之前上傳的檔案沒有紀錄。

對於那些舊檔案，刪圖端點只在**已經被我的一篇貼文或頭像引用**時才放行（所有權無從查起，
能確認的只有引用關係）。因此更早以前就失去引用的檔案（例如當時換頭像留下的舊圖、或換圖
留下的舊附圖）仍然刪不掉，只能由維運直接處理檔案伺服器上的檔案。

這是一條**一次性**的限制：新上傳的檔案都有 `forum_media` 紀錄，不會再回到這個狀態。

### 站內公告的內文不翻譯

只翻譯圍著它的介面文字（標題、時間格式、置頂徽章）。這是刻意的：翻譯管理員寫的文字需要
一套翻譯資料庫，而本站的多語系是純介面層的。

介面上是英文的使用者會看到中文公告 —— 那正確嗎？**取決於你的讀者，而這個決定應該由站方
明確做出**，而不是由實作細節決定。

### `ALLOWED_ADMIN_EMAIL` 的正規化範圍

比對**兩邊**都做 TrimSpace + ToLower，因此帶空白或大寫的寫法不會再靜默失效。

刻意**不**做的正規化是 Gmail 的點號與 `+` 別名（`a.b+c@example.com` 與
`abc@example.com` 是同一信箱）—— 那會把「同一個信箱」變成一個需要業務規則的判斷，而白
名單的重點是「只有這些明確的信箱可以當管理員」，**放寬比對只會讓它更容易被誤加**。

### 通知推播只在單一行程內廣播

即時通知的推播中心（hub）是**行程內的資料結構**：一則通知只會送給「連到產生它的那個實例」
的連線。多實例部署時，同一個使用者的兩個分頁若連到不同實例，其中一個不會即時收到那則通知。

要修就是把 publish 改成 Redis pub/sub（或 stream）再各自轉發，這裡刻意不做：本專案的部署
是單一行程（見 [ARCHITECTURE](ARCHITECTURE.md#即時通知)），而多一層廣播等於多一組「實例
重啟、訊息重播」的失敗模式。

**它不會讓資料不一致**：通知本身寫在 MySQL，未讀數與清單都是查詢來的，漏掉推播的分頁只是
晚一點（下一次載入、或重新連線時的重新同步）才看到紅點 —— 這也是它的優先序不高的原因。

## C. 部署與驗證

### `docker compose` 尚未在本機實測過

撰寫本文時的開發環境沒有可用的 Docker daemon。映像與 compose 檔只經過**靜態檢查**
（YAML 結構驗證 + 每個值與程式碼的設定鍵對照）。

第一次實際部署時請特別留意 `docker compose run --rm backend -check` 的輸出。

### `files_server` 的 S3 模式未經測試

測試覆蓋的是本機模式。S3 後端是刻意保持「最小可用子集」（PUT / DELETE + BasicAuth），
而它的 `saveFile` 會**把整個檔案讀進記憶體** —— 因此 `upload.max_size` 被調到數百 MB 時
那會成為記憶體尖峰。

### 兩個 Go 模組曾經版本不一致

現在兩者都是 `go 1.26.0`。曾經 backend 要 1.25、files_server 要 1.26，會讓只想貢獻後端的
人被一個無關的版本要求擋住。

### `files_server` 的優雅停止

它實作了 `drainUntilTimeout` 與 `stop_grace_period`，但它的請求都是單一的短命上傳／讀取，
影響面遠小於後端。若上傳在停止時被中斷，症狀是「貼文存得下但圖片上傳失敗」。

### `secrets` job 曾有一道會誤擋的範本檢查（已修）

舊版的「確認範本檔不含明文憑證」用一條 ERE 掃兩個 `config.conf.example` 裡**所有未加引號
的值**。那條規則在 GNU grep 上是**合法**的，而且它真的會匹配 —— 範本裡大部分的值本來就
沒有引號（`FORUM_NAME=SB 論壇`、`SERVER_PORT=:8088`、`COOKIE_NAME=forum_forum`），因此那一步
**每次執行都會誤判成有問題而失敗**。它想擋的路徑（把範本填上真實憑證後改名提交）因此
一直沒有一條能走完的檢查 —— 閘門是壞的，只是壞的方向與當初以為的相反。

現在那一步是逐鍵檢查（只驗 `FILES_SERVER_TOKEN`／`REDIS_PASSWORD`／`DB_DSN`／
`GOOGLE_CLIENT_*`／`ES_*` 與 files_server 的 `token`／`password`／`access_key`／`secret_key`
的值是否仍是佔位符），而且**帶著反向自我測試**：它會把三組假憑證塞進暫存副本，任何一組
沒有被判成有問題就讓這一步變紅。留著這一條是因為教訓值得記：一個沒有被反向測試過的
檢查，會安靜地退化成一個只印訊息的路由 —— 而一個**規則太寬**的檢查，會同樣安靜地
退化成一個每次都誤報的路由。

## D. 介面一致性

### `public-profile` 與 `public-posts` 的參數名不一致

| 端點 | 參數 |
| --- | --- |
| `/api/forum/public-profile` | `?key=` |
| `/api/forum/public-posts` | `?user=` |

兩個端點並排時很容易記錯，而且兩者都用同一個長度檢查，因此記錯時症狀是
`400 invalid profile key` 而不是 404。

### `backend/server.log` 是舊版配置留下的

裡面寫的是 `frontend/web/dist`，這個目錄現在不存在了。

### 匯出檔裡的單引號前綴在試算表中不可見、在文字編輯器中可見

這是**刻意的取捨**（CSV 注入防護），但它會被誤認為資料損壞 —— 因此頁面上明寫
「不要要求移除它」。

### CSV 匯出每份上限 5 萬列，達到上限時靜默截斷

串流的 CSV 不能中途插入一行提示，那會讓欄位數不一致。介面上寫出了上限，但**匯出檔本身
沒有標記**。

## E. 清理

### 軟刪除的貼文會在保留期後被清理

貼文刪除是軟刪除（`forum_posts.deleted_at`，見 [`API.md`](API.md#貼文的軟刪除soft-delete)）：
那一列留在表裡，只是任何公開的讀取端都看不到。

**恢復入口已經補上**：後臺的「只顯示已刪除」清單可以還原一篇貼文
（`POST /api/admin/forum/posts/{id}/restore`）。「刪錯能救」因此不再只是資料庫層的性質
—— 但錯過當下就一直沒人發現的誤刪，仍然只有管理員主動去那份清單找才會被救回來。

**清理排程也補上了**（`backend/forum/purge`）：超過 `POST_RETENTION_DAYS`（預設 90 天）
的軟刪除貼文會被硬刪，連同它的留言、按讚、收藏與指向它的檢舉工單 —— 同一個交易裡
一起消失。附圖在「不再被任何貼文或頭像引用」時會透過檔案伺服器刪掉；待刪檔名與貼文
交易一起寫進 `forum_media_deletions`，刪檔失敗或程式在交易與刪檔之間崩潰時，下一個
tick 會重試。沒有檔案伺服器（`FileDeleter` 為 nil）時檔案與它的所有權紀錄都留著
（否則會變成沒有任何程式認得的孤兒檔案），也不會寫入佇列。

剩餘的限制與取捨：

- **保留期是硬期限**：到期之後就不可逆了。90 天與稽核紀錄的保留期相同，因為管理員用
  稽核與檢舉對帳時，兩邊需要同一尺度。設定成 7 天與設定成 90 天的差別，在啟動之後
  就看不到 —— 因此 `-check` 的報告刻意印出這個值。
- **每個 tick 有工作量上限**：每小時一次、每個 tick 最多清 2,000 列。累積量因此以
  每小時 2,000 列的速度排掉，而不是一次排完（一次排完會佔住連線池、並讓論壇的正常
  請求在那一整段時間裡排隊）。
- **過期到被清理之間有一個窗口**：後臺的「只顯示已刪除」清單只過濾
  `deleted_at IS NOT NULL`，**沒有**保留期條件 —— 一篇剛好過期的貼文在下一個清理
  tick 之前仍然列得出來、仍然可以還原。清理排程每小時跑一次，因此那個窗口是
  「一個小時加上尚未排到的批次」。
- **日別彙總不會跟著變**：`/admin/stats` 的 `forum_daily_stats` 記的是「那天產生了
  多少」的**歷史量**（軟刪除的貼文照算），因此清理排程刻意不改變那些數字 ——
  文章確實在那天被產生了，只是後來被回收了。

### ES 的幽靈文件：會被定期對帳收斂

貼文刪除會移除 ES 文件（`unindexForumPost`），而那是 best-effort：ES 剛好短暫不可用時，
刪除會成功而索引留下**幽靈文件**（一篇已經不存在的貼文仍在索引裡）。目前已緩解的部分：

- 搜尋端會拿回來的 id 用 MySQL 可見性比對，把幽靈從結果與 `total` 中挑掉，並在該頁因此
  變短時向後補齊（`searchForumPostIDsElasticsearch`），所以「宣稱 10 筆、畫面 9 張卡」與
  「最後一頁整頁空白」不會發生。
- 組裝階段（`loadForumPostsByIDs`／`loadAdminForumPostsByIDs`）保留第二道過濾。
- **定期對帳已經補上**（`ReconcileSearchIndex`，每六小時一次）：把 ES 與 MySQL 的可見貼文
  id 集合比對，刪掉多出來的那些文件。因此幽靈不會無限期留著。

仍未解的部分：

- 對帳最多落後六小時：那段期間裡「搜得到但點進去 404」仍可能發生。
- 對帳要**把兩邊的 id 集合都讀進記憶體**（MySQL 一邊、ES 一邊），成本與站上貼文總數
  成正比。對這個規模夠用，但它是這條路徑唯一的線性記憶體成本。
- 啟動時的全量重建（`RebuildSearchIndex`）仍然只補索引、不刪多出來的文件 —— 刪多出來的
  那些是對帳的工作。因此「服務停機期間被刪掉的貼文」要等到第一輪對帳才會從索引裡消失。

### 公告只有一則生效，且不會被刪除

只有停用，沒有刪除。保留歷史是為了回答「這則是什麼時候、經誰發布的」，那正是稽核紀錄
之外的另一半脈絡。

代價：`forum_announcements` 會隨時間累積列數。**若要清理過期且已停用的公告，目前得直接
動資料庫。**

### 稽核紀錄沒有刪除紀錄的 API

唯一清理途徑是時間式的 `audit.Pruner`（`AUDIT_RETENTION_DAYS` 天，預設 90）。

一個能刪除自己紀錄的稽核日誌等於沒有稽核日誌，所以這是刻意的。

### `MEDIA_TOKEN_TTL_SECONDS` 的兜底值是 30 天

對正式環境明顯過長。已緩解：正式環境（`COOKIE_SECURE=true` 或 `PUBLIC_BASE_URL` 為
https）未明確設定時，`config.Validate` 會讓**啟動被拒絕**，並由 `-check` 在部署前指出。

刻意「設成 30 天」是允許的 —— 那代表部署者知道自己在做什麼。

### `ReadTimeout` 與 `WriteTimeout` 刻意不設

- `ReadTimeout` 會連請求本文一起計時，而**貼文附圖的本文可達 50 MB 且還要轉送給檔案
  伺服器**。
- `WriteTimeout` 會在回應寫完前砍斷連線，而 **CSV 匯出的耗時就落在這段裡**。

`ReadHeaderTimeout` 與 `IdleTimeout` 有設，因此 Slowloris 與 keep-alive 連線累積這兩個
曝露面是關掉的。

補上前兩項時必須同時評估上傳與匯出路徑，而不是照常見範例填 30 秒。

### `forum_post_comments.post_id` 沒有外鍵

因此「父文章存在嗎」永遠只能由應用層自己問。隨著貼文改成軟刪除（`deleted_at`），
這個問題從「存在嗎」變成「還活著嗎」，而問的地方也比以前多：

| 位置 | 問法 |
| --- | --- |
| 使用者留言（`forum_handlers.go`） | `forumPostVisibleByID` |
| 使用者按讚（`forum_handlers.go`） | 交易內的 `COUNT(*)` |
| 使用者收藏（`forum_bookmark_handlers.go`） | 交易內的 `COUNT(*)`（與按讚逐字同形） |
| 留言列表／編輯／刪除（`forum_handlers.go`） | 讀取端一次 `forumPostVisibleByID`；寫入端把 `EXISTS ... deleted_at IS NULL` 放進同一句 |
| 後臺代留言（`forum_admin_handlers.go`） | `COUNT(*)` |
| 以使用者身分代留言（`user_admin_handlers.go`） | `COUNT(*)` |
| 後臺還原（`forum_admin_handlers.go`） | `SELECT ... WHERE id = ? AND deleted_at IS NOT NULL` —— 問的是相反的那一邊（它**還**是刪除狀態嗎） |
| 檢舉目標（`forum_handlers.go` 與 `forum_admin_handlers.go`） | 動態表名搭配動態條件（貼文帶 `deleted_at IS NULL`，留言不帶） |

一律帶 `deleted_at IS NULL`（唯一的例外是檢舉目標裡的**留言** —— 它沒有軟刪除狀態，
見上表最後一列），因此「對一篇已刪除的貼文留言／按讚／編輯／刪除／檢舉」一律 404，
而**已刪除貼文底下的留言也讀不到**—— `GET /api/forum/posts/{id}/comments` 曾經是這個
規則唯一的漏網之魚：貼文詳情頁已經 404，留言卻仍能沿著那支端點讀到。

貼文改成軟刪除之後，「刪文章時要手動清理留言」這個需求**少了一半**：母文章那一列還在，
留言與按讚只是跟著一起不可見。若日後把刪除改回硬刪除，連動清理的需求就會回來，而那時
應該直接宣告 `ON DELETE CASCADE`，而不是繼續用應用層補。

### schema 沒有 migration 版本控制

只有 idempotent 步驟（`CREATE TABLE IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN IF NOT
EXISTS`、`INSERT IGNORE`），**沒有降級路徑**。

好處是空資料庫直接啟動即可、不需手動匯入 SQL；代價是沒有辦法把 schema 降回去。

### 部分留言與檢舉的 handler 沒有逐支重複的身分檢查

`handleForumPostUpdate`、`handleForumCommentUpdate`、`handleForumCommentDelete` 與
`handleForumPostDelete` 都在開頭確認一次登入狀態（縱深防禦），但
`handleForumComments`（POST 留言）與 `handleForumReport` **沒有** —— 它們的安全性完全
來自中介層的 `requireLoginForWrite`。

這兩條路由目前不會被未登入者呼叫到，所以**不是可利用的缺口**；但若日後有人把它們註冊到
別的路徑上，就會同時失去中介層與 handler 兩層。
